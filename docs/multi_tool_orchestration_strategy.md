# Multi-Tool Orchestration Strategy

This document outlines the architectural strategy for handling multi-layer, multi-tool SVG jobs. It defines the separation of responsibilities between the **Job Orchestrator** and the **Math Pipeline**, ensuring the system can support complex tasks (like tool interleaving and path optimization) without introducing unnecessary complexity to the core physics engine.

---

## 0. Two Execution Modes

The protocol layer (`host/protocol/packets.py`) already defines two distinct production modes. The Orchestrator strategy must be consistent with both:

| Mode | Who runs the pipeline | What the host sends | How Orchestrator tracks position |
|---|---|---|---|
| **Host-bake** (current) | Host PC | Pre-computed `MicroSegment` packets (`0xAB`) | Pipeline returns final integer step position |
| **Pico-local** (future C++ port) | RP2350 | Raw `SplineTile` Bézier packets (`0xAD`) + `ToolConfig` (`0xAC`) | Dead-reckoned from the geometry sent |

In both modes, the Orchestrator is the brain. Only the mechanism of position tracking differs.

---

## 1. The Core Insight: Block-Scoped Pipeline, Global Orchestrator

The fundamental design principle is a clean split of state ownership between the pipeline and the Orchestrator:

*   **The Pipeline** (Stages 3–8: Repair, Flatten, Constrain, Plan, Discretize) carries rich internal state during a block — position accumulators, A-axis rotation, velocity profiles — but that state is **contained entirely within the block**. It is initialised at block start, used during execution, and discarded at block end. The pipeline does not feed its state back to the Orchestrator. It has no knowledge of what came before or what comes next.
*   **The Orchestrator** (e.g., `host/production/planner.py`) holds the **global machine state** for the duration of the entire job. It reads the whole SVG, groups paths into logical blocks, decides execution order, manages tool changes, injects travel moves between blocks, and tracks the machine's physical position and A-axis rotation across all blocks.

> [!TIP]
> Because the pipeline's state is self-contained per block, orchestration logic (layer ordering, interleaving, travel optimization) can evolve independently without touching the pipeline stages. A smarter Orchestrator never requires a smarter Pipeline.

---

## 2. Pass-by-Pass Execution Flow

Instead of the current method (entire SVG layers thrown at the pipeline in document order), the Orchestrator implements a **Pass-by-Pass** model:

### Step A: Path Grouping and Sorting
The Orchestrator parses the SVG and groups subpaths into logical **Blocks**. Each block has one tool and one contiguous sequence of paths. The Orchestrator decides the block order — document order by default, with smarter ordering (e.g., inner-before-outer, nearest-neighbour) as future enhancements.

### Step B: Global State Tracking
The Orchestrator maintains the machine's global physical state in **integer steps** throughout the job:

```python
global_pos_x: int   # X axis, integer steps from home
global_pos_y: int   # Y axis, integer steps from home
global_a_phys: int  # A axis, cumulative physical steps (unwind reference)
```

Integer steps (not mm) keep the Orchestrator in exact agreement with the pipeline's own float→int rounding, preventing drift across block boundaries.

**In host-bake mode:** `global_pos_x/y` are updated from the **integer step position returned by the pipeline** after each block. This is the only correct source — the pipeline's own float accumulator rounding determines the true final position.

**In Pico-local mode:** The Pico never sends step data back to the host. The Orchestrator **dead-reckons** position from the Bézier geometry it sent — computing the expected endpoint of the last curve in integer steps. The `getpos` control-plane command (`link.command("getpos")`) is available to confirm position after each block completes if needed.

### Step C: The Travel Injection
Before executing the next Block, the Orchestrator knows the starting coordinate of that block's first path and the current `global_pos_x/y`.

*   **In host-bake mode:** The travel jog is generated by invoking the **pipeline's own jog logic** (not a separate implementation). The travel move is expressed as a straight-line subpath prepended to the block's geometry, so the pipeline's rate-limiting and Bresenham logic apply consistently.
*   **In Pico-local mode:** The travel move is sent as a straight-line `SplineTile` packet tagged with `jog_feed` and `TILE_PATH_START`/`TILE_PATH_END` flags. The Pico's C++ pipeline executes it identically to a cutting path. No special "travel" logic is needed on the MCU.

### Step D: Block Execution
The Orchestrator dispatches the block to the pipeline (host-bake) or streams it to the Pico (Pico-local). On completion:
*   The Orchestrator updates `global_pos_x`, `global_pos_y`, and `global_a_phys`.
*   The block boundary contracts (see Section 3) are enforced.
*   *Repeat for the next Block.*

### Step E: Batching Policy
The Orchestrator **batches aggressively**. All paths for the same tool in a contiguous logical group are dispatched in a single block. Splitting into individual-path blocks (for registration or pop-out protection) is a deliberate opt-in mode, not the default. Unnecessary splitting imposes a full stop-start velocity penalty at every block boundary.

## 3. Block Boundary Contracts

All block transitions — whether a tool change or the next batch of the same tool — must obey these invariants unconditionally:

### Z-Axis: Always Leave Lifted
At the **end of every block**, Z is raised. At the **start of every block**, Z is lowered before cutting begins. This rule applies regardless of `lift_height` in the tool profile. It gives the machine a safe, known Z state between blocks.

### A-Axis: Always Return to 0° Between Blocks
At the **end of every block**, the Orchestrator commands an explicit A-axis home-to-0° move — an absolute return to the physical 0° reference, not a minimum-rotation unwind. This eliminates wire-twist accumulation across block boundaries and is directly compatible with both execution modes: in Pico-local mode the MCU cannot carry A-axis state between independently streamed blocks, so the host must always start the A axis at a known reference.

### Tool Changes
If Block $N$ uses a Pen and Block $N+1$ uses a Knife:
1. Block $N$ completes. Z is raised. A is homed to 0°.
2. A `MSEG_FLAG_PAUSE` is injected into the `.plan` file (host-bake), or a pause command is issued over the control plane (Pico-local).
3. The user swaps the tool, or the dual-head firmware selects the new head.
4. The Orchestrator proceeds to **Step C** for Block $N+1$.

### Layer Batching Policy
Each SVG layer is treated as its own block by default. The Orchestrator may merge same-tool layers into one block when there is no reason to separate them. The user does not micromanage this — the Orchestrator owns the batching decision.

---

## 4. Advantages of this Architecture

*   **Perfect Interleaving:** Finish internal draws/creases before the perimeter cut, part-by-part, preventing pop-out and material shift.
*   **Travel Optimization:** The Orchestrator can sort blocks by proximity (nearest-neighbour, TSP) without modifying a single line of pipeline math.
*   **Format Compatibility:** The `.plan` binary format is just a sequential list of `ToolOperation` chunks. It natively supports any block ordering the Orchestrator produces.
*   **Flexibility Without Coupling:** Orchestration logic (layer ordering, inner/outer sequencing, registration grouping) evolves independently of the pipeline stages.

---

## 5. Compatibility with the RP2350 C++ Port

The Orchestrator/Pipeline split maps cleanly onto the existing two-mode wire protocol (`host/protocol/packets.py`):

*   **MCU Stays Lightweight:** The Pico never parses SVG documents, evaluates layer logic, or runs path-sorting algorithms. It receives one block at a time and executes it.
*   **No Return Data Needed:** In Pico-local mode the Pico streams motor steps directly to the stepper controllers. It never sends step data back to the host. The Orchestrator dead-reckons position from the geometry it dispatched. This is correct by construction — the Orchestrator computed the block geometry, so it knows where the block ends in integer steps.
*   **Travel Moves as Simple Geometry:** Inter-block travel is a straight-line `SplineTile` at the front of each block. The Pico's pipeline executes it identically to a cut path. No MCU-side "travel mode" is required.
*   **A-Axis Home Between Blocks:** The unconditional A-home rule means each block always starts with the A axis at a known physical reference. The Pico never has to query or inherit A-axis state from a previous block.
*   **Block Size:** When scoping the C++ port, the Orchestrator must enforce a maximum block size so each block fits within RP2350 working RAM (the flatten stage expands Bézier curves into a large `Sample` array). This is a Pico-port constraint that does not affect the current host-bake path.
