**Options for where truth lives:**

**A. TOML → generated C header** (codegen)
`machine.toml` → Python reads directly, a script emits `machine_config.h` → PlatformIO builds it in. Single source, explicit sync, works offline. Needs a pre-build step and a reflash on config change.

**B. Pico receives config at connect time** (CMD_SET_CONFIG)
Host sends machine params as a command packet on startup. Pico holds them in RAM/flash. No reflash for config changes. But: Pico has no config until host connects — local production in Phase 2 needs the Pico to be self-contained, so you'd still need flash persistence, which makes this nearly as complex as A without the single-source benefit.

**C. Keep separate, sync manually**
Pico `machine_config.h` hardcoded, Python `config.py` separately. Fine for Phase 1 (Pico doesn't interpret motion, just emits). Becomes a correctness hazard the moment Phase 2 lands.

---

**Recommendation: A, in two steps**

**Step 1 — now (Phase 1 complete):** Implement `load()` to read `machine.toml`. The TOML has `[machine.x]`, `[machine.y]`, etc. matching `AxisConfig` fields. `_default_machine()` stays as the in-code fallback. Host picks up the TOML automatically; Pico still has a handwritten `machine_config.h` (it only needs node-map + invert for the emit layer — small, stable, low sync risk).

**Step 2 — before Phase 2:** Add `tools/gen_machine_config.py` that reads `machine.toml` and writes `src/rp2350/machine_config.h`. Wire it into PlatformIO `extra_scripts` so the header is always regenerated on build. From that point forward, editing the TOML and running `pio run` is the only config workflow — both sides stay in sync automatically.

`QualityConfig` follows the same pattern when the Pico planner lands: add a `[quality]` section to the TOML, extend the codegen, done.

**Claude:** Good instinct — self-describing files are genuinely useful. Quick premortem:

**What it solves well**
- `.bin` files become auditable: `validate_plan` can extract and display the config that produced them
- Mismatch detection: Pico receives the preamble, compares against its own config, rejects or warns if they diverge — catches sync bugs at runtime rather than silently running wrong
- Reproducibility: you can always regenerate from the embedded config

**The fundamental snag**
Microsegments are *already in steps* — the config is consumed at generation time. The embedded config is an audit trail, not operational data. If the Pico's calibration drifts (you re-measure and get `steps_per_unit=162` instead of `160`), the embedded config says "160" but the segments are *already encoded for 160*. The Pico executing those steps doesn't care what config header says — it just fires pulses. "Use the embedded config" doesn't mean anything in that case; the geometry is baked into the step counts.

**Local production has no file**
When the Pico generates segments locally they live in RAM — there's no file with a header. So "local: use onboard config" is the only option there anyway. The embedded config idea only applies to the host-produced path.

**It doesn't replace sync, it surfaces mismatches**
The Pico still needs its own config to know what the machine *currently* is. Embedding config in the file is most useful as a **validation handshake**: Pico receives config preamble → compares against its own → accepts or rejects. That's genuinely useful. But it means the Pico must still have authoritative config somewhere — the sync problem is still there, it's just caught at runtime instead of silently corrupting motion.

**Verdict**
Embed it — it's worth doing for auditability and the mismatch-detection handshake. But treat it as a complement to the TOML→generated header approach, not a replacement. The two together give you: static sync guarantee (TOML codegen) + runtime tripwire (embedded config preamble). Either alone leaves a gap.

The file format question: header before the packet stream, or a special leading packet? Leading packet fits the existing framing (length-prefixed packets) without a new parser.

**Claude:** Yes, that's a clean and safe assumption. Let me work out what actually falls into each bucket.

**Production-involved** (changes the output steps/intervals):
- `steps_per_unit`, `f_cpu`, `invert` — the step math
- `max_rate`, `accel` — velocity planning
- `QualityConfig` — flattening resolution, interval choice
- `MotionConfig` — feed limits, lift, jog
- `ToolProfile` — corner handling, tangential choreography

**Not production-involved** (Pico emit layer only):
- Node map (`AxisConfig.node`) — which ATtiny bit-slot gets which axis
- `present` — skip inactive axes
- `max_travel` — soft limits (deferred)

That second list is tiny. And crucially — **the Pico emit layer right now doesn't even consume most of the first list**. It just fires the step/dir bits it's handed. The entire first list is the host's problem when producing.

So the natural split:

| Config | Host (Python) | Pico emit layer | Pico planner (Phase 2) |
|---|---|---|---|
| steps_per_unit, f_cpu, invert | ✓ authoritative | — not needed | ✓ must agree |
| QualityConfig, MotionConfig | ✓ authoritative | — not needed | ✓ must agree |
| Node map, present | ✓ (informational) | ✓ authoritative | ✓ must agree |

**The two-location reality you're describing is already the truth** — the Pico emit layer has its own hardcoded node map, and the host has `config.py`. They don't talk. You're just proposing to make it explicit and stop feeling bad about it.

The one honest risk: when Phase 2 arrives and the Pico runs its own planner, the two production configs need to agree with the physical machine — not with each other through software, but because they're both measuring the same hardware. That's a calibration discipline problem, not an architecture problem. The embedded-config-in-binary idea you had earlier is actually the right tool for catching drift: if host-produced binaries say `steps_per_unit=160` and the Pico's planner is using `162`, someone miscalibrated — the mismatch is visible.

So the architecture becomes:
- Host config is self-contained, self-describing, embedded in the binary
- Pico has its own config for the emit layer now, full planner config later
- They agree because they describe the same physical machine, not because software enforces it
- Drift surfaces through the binary header mismatch, not through silent wrong motion

That's simpler and more honest than trying to build sync infrastructure. Agree?

**Claude:** Exactly right, and it closes the loop cleanly. Let me lay out what this implies end-to-end:

**Pico is the authority**
It holds the calibrated config in flash (LittleFS or similar). It's the closest to hardware. On playback it validates the incoming binary's embedded config against its own — mismatches are rejected or warned, not silently executed wrong.

**The pull/push workflow**
```
pico-config pull  →  machine.toml   (Pico → host, human-editable)
  <edit>
pico-config push  ←  machine.toml   (host → Pico, stored to flash)
```
Two new USB serial commands: `CMD_GET_CONFIG` and `CMD_SET_CONFIG`. Host gets a TOML (or JSON) it can edit and write back. Pico validates the incoming config before storing (range checks, sanity).

**Host production is config-agnostic**
`run(svg, machine, ...)` doesn't know or care if `machine` came from a pull, a local `config.py`, or a command-line flag. The pipeline just consumes whatever it's handed. That's already true today — the pull just becomes the canonical way to obtain it.

**The full data flow:**
```
Pico flash (authoritative)
    │ pull
    ▼
machine.toml  ──►  host pipeline  ──►  .bin  (config embedded as header)
                                         │
                                         │ playback
                                         ▼
                                       Pico validates header vs flash
                                       accept / reject
```

**Local production (Phase 2) fits naturally**
Pico reads from its own flash directly — no pull needed. Config provenance is identical whether the planner runs on host or on Pico.

**What this defers gracefully**
The TOML codegen / generated C header idea goes away. Pico config lives in flash, loaded at runtime — no build step, no header sync. The flash IS the C header.

The one new complexity: Pico needs a serialization format for `CMD_GET_CONFIG` / `CMD_SET_CONFIG`. A fixed-layout binary struct is simplest (matches what you'd put in a generated header anyway); the host-side tool wraps it in TOML for human editing.
